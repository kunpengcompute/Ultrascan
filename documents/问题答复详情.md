## 1. `fdrBuildProtoInternal` 里的 `choosePbeEngine` 和 `chooseNeoFdrEngine` 有什么区别？是不是复制 Neo 的逻辑？这一部分在做什么？

对应代码：
- [fdr_compile.cpp](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_compile.cpp:878)
- [fdr_engine_description.cpp](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_engine_description.cpp:214)
- [fdr_engine_description.cpp](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_engine_description.cpp:319)

**结论**
是的，当前 `choosePbeEngine(...)` 和 `chooseNeoFdrEngine(...)` 的逻辑几乎是同构的，差别主要只有：
1. Neo 用 `getNeoFdrDescriptions(...)`，engine id 是 `1`
2. PBE 用 `getPbeDescriptions(...)`，engine id 是 `2`

定义上它们甚至都只塞了一个相同形状的描述：
- Neo: `{1, 64, 8, 0}`
- PBE: `{2, 64, 8, 0}`

对应代码：
- [fdr_engine_description.cpp](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_engine_description.cpp:62)
- [fdr_engine_description.cpp](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_engine_description.cpp:68)

**这一部分到底在做什么**
它**不是**在构建 PBE 自己的 22-bit 一级哈希表。  
它做的是：

1. 选一个 `FDREngineDescription`
2. 用这个描述去跑：
   - `assignStringsToBuckets(...)`
   - `addIncludedInfo(...)`
   - `HWLMProto(...)`
3. 让 PBE 先复用现有 FDR/Neo 的 proto 构建链路和外层编译框架

也就是说，`choosePbeEngine(...)` 选出来的 `bits/stride/numBuckets`，主要服务于：
- bucket 分配
- included info
- 外围 `FDRCompiler` / proto 流水

而**真正的 PBE L1/L2 哈希结构**，是在后面：
- [buildPBEArtifacts(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:727)
里单独构建的。

**这是不是有问题**
不是“功能错误”，但确实是一个**设计借壳**。

当前这样做的好处：
1. 快速接入现有 FDR 编译链路
2. 可以直接复用 bucket/included/外围 table builder
3. 少改很多现有代码

当前这样做的问题：
1. `choosePbeEngine` 的 heuristics 其实还是 Neo 风格的
2. 这些 heuristics 不一定最适合 PBE
3. 代码读起来会让人误以为“PBE 的编译策略 = Neo 的编译策略”

**更准确地说**
当前 PBE 是：
- **外层 proto/bucket 选择借用 Neo/FDR**
- **内层真正扫描结构用 PBE 自己的 artifacts/blob**

所以它不是“完全复制 Neo”，但确实有一层明显的 Neo 兼容壳。

## 2. 进入 PBE 的前置条件需要调整，规则数上限暂定为 `100000000`

对应代码：
- [analyzePBEFeasibility(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:771)
- [canBuildPBE(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:857)

当前上限判断：
- [pbe_compile.cpp:808](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:808)

```cpp
if (lits.size() > std::numeric_limits<u16>::max()) {
    local.reason = PBEFeasibilityReason::TOO_MANY_LITERALS;
    ...
}
```

**这里不能直接改成 `100000000`**
因为当前结构本身还不支持这么大的规则规模，至少有 4 个硬限制。

**限制 1：`ruleIndex` 现在是 `u16`**
对应结构：
- [pbe_compile.h](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:51)
- [pbe_runtime.h](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_runtime.h:58)

字段：
- `u16 ruleIndex[PBE_RULE_SLOTS_PER_ENTRY]`

写入点：
- [pbe_compile.cpp:612](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:612)

所以只要 literal 下标超过 `65535`，这里就已经不成立了。

**限制 2：L1 的 count 字段只有 14 bit**
对应编码：
- [pbe_compile.cpp:108](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:108)
- [pbe_compile.h:17](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:17)
- [pbe_compile.h:19](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:19)

L1 value 的布局是：
- 低 18 bit：secondary offset
- 高 14 bit：连续 L2 entry 数

所以单个一级 key 最多只能表示：
- `16383` 个 L2 entry
- 每个 L2 entry 4 条规则
- 也就是单 key 最多 `65532` 条规则

如果很多规则落到同一个 key，上限会先炸掉。

**限制 3：`literalBlob` 和 `litOffset` 还是 `u32`**
对应结构：
- [pbe_compile.h:63](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:63)
- [pbe_runtime.h:70](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_runtime.h:70)

字段：
- `u32 litOffset`
- `u32 literalBlobSize`

如果总规则字节量超过 4GB，这里也不成立。

**限制 4：实际内存成本会非常大**
即使不碰类型溢出，`100000000` 条规则在当前结构下：
- `ruleMeta`
- `literalBlob`
- L2 entries
- bucket map
都会是非常重的内存压力。

**所以正确结论是**
“把规则数上限改成 `100000000`” 不是一个 check 改动，而是一个**结构级改造**。

至少需要：
1. `ruleIndex` 从 `u16` 改成 `u32`
2. 重新设计 L1 value 里的 `count|offset` 编码
3. 重新评估 `literalBlobSize/litOffset`
4. 重新评估构建期内存模型

**我建议**
这一点如果要做，我建议单独开一轮改造计划，而不是直接把：
- [pbe_compile.cpp:808](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:808)
改成 `100000000`

否则代码会变成“前置检查放行了，但后面结构仍然装不下”。

## 3. `buildExtractDescriptor()` 里 `bextToKeyBit` 保存的是什么？“packed bit 到 key bit 的重映射”是什么意思？有没有排序？

对应代码：
- [buildExtractDescriptor(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:125)

关键逻辑：
- [pbe_compile.cpp:140](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:140)
- [pbe_compile.cpp:148](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:148)
- [pbe_compile.cpp:150](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:150)
- [pbe_compile.cpp:151](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:151)

**先说结论**
`bextToKeyBit` 保存的**不是 source bit index 本身**，而是：

**“`bext` 压缩结果里第 `i` 个 packed bit，应该回填到 key 的哪一位”**

也就是：
- packed bit index -> key bit index

**为什么需要它**
因为当前 key 的位编号，是按 `selectors` 的顺序定义的。  
而 `bext`/packed extract 的输出顺序，不是 selector 顺序，而是：

**按 source bit 在 `window64` 里的位置从小到大压缩**

这两个顺序通常不一样，所以必须做一次重映射。

**当前实现过程**
`buildExtractDescriptor()` 先构造：

```cpp
(bitIndex, selectorIndex)
```

其中：
- `bitIndex` = 这个 selector 对应的 `window64` 源 bit 位置
- `selectorIndex` = 这个 selector 在 key 里的逻辑位序

然后：
- [pbe_compile.cpp:148](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:148)
对 `bitOrder` 做排序

```cpp
std::sort(bitOrder.begin(), bitOrder.end());
```

默认按 pair 的第一元素排序，也就是：

**按 source bitIndex 升序排序**

然后：
- [pbe_compile.cpp:150](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:150)
把这些 source bits 填进 `bextMask`
- [pbe_compile.cpp:151](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:151)
把对应的原始 `selectorIndex` 填进 `bextToKeyBit[i]`

**所以它有没有排序**
有，而且是：

**按 source bit index 从小到大排序**

不是按 key bit 从大到小，也不是按 key bit 从小到大。

**举个例子**
假设 selector 顺序是：

1. `selector0 -> source bit 11`
2. `selector1 -> source bit 2`
3. `selector2 -> source bit 20`

那么：
- key bit 0 对应 source bit 11
- key bit 1 对应 source bit 2
- key bit 2 对应 source bit 20

排序后 source bits 变成：
- 2
- 11
- 20

所以：
- packed bit 0 来自 source bit 2，它应该写回 key bit 1
- packed bit 1 来自 source bit 11，它应该写回 key bit 0
- packed bit 2 来自 source bit 20，它应该写回 key bit 2

于是：

```text
bextToKeyBit = [1, 0, 2]
```

**这就是“packed bit 到 key bit 的重映射”**

**这对运行期的意义**
运行期在：
- [pbeExtractKeyBext(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:262)
- [pbeRemapPackedBits(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:240)

会先得到 packed bits，再按 `bextToKeyBit` 回填回逻辑 key。

所以这个设计是为了：
1. 让 `bextMask` 可以按 source bit 升序直接工作
2. 又不破坏当前 key 的 selector 位定义

这一步是合理的。

## 4. `buildPrimaryBitmap()` 是怎么实现的？结构是什么样的？举个例子

对应代码：
- [buildPrimaryBitmap(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:165)
- [pbePrimaryBitmapSet(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:157)

对应结构：
- [PBEPrimaryHashTable](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:43)
- [PBEPrimaryHashBitmap](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:47)

**结构本质**
它是一个**固定大小的 dense bitmap**，不是只给非空项单独建条目。

也就是说：
1. 一级哈希表 `offsets` 的项数固定是 `2^22`
2. 位图的 bit 数也固定对齐到这个项数
3. 某个一级表项非空，就把对应 bit 置 1
4. 否则保持 0

大小计算：
- [pbePrimaryBitmapBytes(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:120)

```cpp
(primaryCount + 7) / 8
```

所以当 `primaryCount = 2^22` 时：
- bitmap bytes = `524288`

这和你 `PBEInspect` 输出里的：
- `bitmapBytes=524288`
是一致的。

**构建流程**
1. 清空 `bits`
2. 按 `primaryCount` 分配固定字节数并全部置 0
3. 遍历 `primaryHashTable.offsets`
4. 如果 `offsets[i] != 0`，就对 `bits[i/8]` 的 `(i%8)` 位设 1

关键判断：
- [pbe_compile.cpp:173](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:173)

```cpp
if (primaryHashTable.offsets[i]) {
    pbePrimaryBitmapSet(&primaryHashBitmap->bits, i);
}
```

**举个小例子**
假设一级表只有 16 项：

```text
offsets[0] = 0x40001
offsets[1] = 0
offsets[2] = 0
offsets[3] = 0x40008
offsets[4] = 0
offsets[5] = 0
offsets[6] = 0
offsets[7] = 0
offsets[8] = 0
offsets[9] = 0x40020
offsets[10..15] = 0
```

那 bitmap 需要 2 个字节。

第 0 个字节表示索引 0..7：
- index 0 有值 -> bit0 = 1
- index 3 有值 -> bit3 = 1

所以：
```text
bits[0] = 00001001b = 0x09
```

第 1 个字节表示索引 8..15：
- index 9 有值 -> bit1 = 1

所以：
```text
bits[1] = 00000010b = 0x02
```

**运行期判断方式**
- [pbePrimaryBitmapHasValue(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:410)

```cpp
bitmap[idx / 8] & (1U << (idx % 8U))
```

**所以回答你的问题**
它不是“只存非空项”的稀疏结构，  
而是：

**项数固定为 L1 最大项数，只有部分 bit 有值的 occupancy bitmap。**

## 5. `fdrBuildTableInternal()` 这里会重建一遍 `artifacts`，原先的 `artifacts` 是否正常释放了？

对应代码：
- [fdrBuildTableInternal(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_compile.cpp:967)

这里确实做了两份 artifacts：

1. proto 阶段：
- [fdr_compile.cpp:905](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_compile.cpp:905)
把 `pbeArtifacts` 存进：
```cpp
proto->pbeArtifacts = ue2::make_unique<PBECompileArtifacts>(...)
```

2. table 阶段：
- [fdr_compile.cpp:976](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/fdr_compile.cpp:976)
又局部构造：
```cpp
PBECompileArtifacts rebuiltArtifacts;
```

**为什么重建**
因为 proto 构建后，`proto.lits` 还可能被后续流程改写，尤其是：
- literal id 被 Rose 程序 offset 重写

所以 table build 必须基于最终 `proto.lits` 重建，否则会拿到 stale id。

这一步是必要的。

**原来的 artifacts 会不会泄漏**
不会，当前是 RAII，生命周期是正常的。

具体来说：

1. `proto->pbeArtifacts`
- 由 `unique_ptr` 持有
- 会在 `HWLMProto` 析构时自动释放

2. `rebuiltArtifacts`
- 是栈上局部变量
- `fdrBuildTableInternal(...)` 返回时自动销毁

3. `pbeBlob`
- 是 `bytecode_ptr<u8>`
- 成功时 move 进 `FDRCompiler`
- 失败时离开作用域自动释放

**所以没有内存泄漏**
但确实有一个现象：

**会暂时存在两份 artifacts**
- 一份缓存的 proto artifacts
- 一份 table build 的 rebuiltArtifacts

这不是 leak，而是**冗余临时占用**

**我的判断**
当前设计是“正确但不够干净”：
1. 正确性上需要重建
2. 生命周期上没问题
3. 但 proto 阶段缓存的那份 artifacts 在 table 阶段已经不再参与最终 blob 生成，更多是调试/中间产物

## 6. 一级 / 二级哈希表的构建流程，需要更详细描述

对应代码：
- [buildHashTables(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:532)

我按真正流程展开。

### 第一步：确定 L1 固定大小
- [pbe_compile.cpp:544](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:544)

```cpp

```

当前 `PBE_KEY_BITS = 22`：
- [pbe_compile.h:16](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:16)

所以 L1 永远是：
- `2^22 = 4,194,304` 项

每项一个 `u32`。

### 第二步：预留 L2[0] 为空项
- [pbe_compile.cpp:547](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:547)

```cpp
secondaryHashTable->push_back(PBESecondaryHashEntry{});
```

这样 `secondaryOffset = 0` 可以自然表示空引用。

### 第三步：计算每条规则的 `keyValue` 和 `keyMask`
- [pbe_compile.cpp:556](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:556)
- [computeKeyValueMaskForLiteral(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:45)

对每条 literal：
1. 遍历 selectors
2. 看这个 selector 对应 bit 在该规则里是不是 care
3. care 就在 `keyMask` 相应位置 1
4. care 且值为 1，就在 `keyValue` 相应位置 1

所以：
- `keyValue` = 规则在 cared selectors 上的值
- `keyMask` = 哪些 selectors 对这条规则是 cared

### 第四步：决定规则进哪个 L1 bucket
关键逻辑：
- [pbe_compile.cpp:562](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:562)

```cpp
const u32 bucketKey = (keyMask == fullMask) ? keyValue : 0U;
```

也就是当前的**单 key 策略**：

1. 如果这条规则对 22 个 key bit 全部 care
- 进 exact bucket
- `bucketKey = keyValue`

2. 如果存在 don't-care bit
- 进 wildcard bucket
- `bucketKey = 0`

所以当前所有 partial mask 规则都会堆到：
- `L1[0]`

### 第五步：按 bucketKey 聚合规则
- [pbe_compile.cpp:550](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:550)

```cpp

```

最后得到：
- 一个 key
- 对应一组 literal index

### 第六步：给每个一级 key 分配连续 L2 entries
对每个 key bucket：
- [pbe_compile.cpp:576](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:576)

```cpp
entryCount = ceil(bucketRules / 4)
```

因为每个 L2 entry 固定 4 条规则：
- [pbe_compile.h:20](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:20)

然后：
- [pbe_compile.cpp:594](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:594)
记录这个 key 对应的起始 `secondaryOffset`

L1 value 的编码：
- [encodePrimaryValue(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:108)

格式是：

```text
u32 primaryValue =
    [ high bits: entryCount ][ low 18 bits: secondaryOffset ]
```

### 第七步：填充每个 L2 entry
每个 chunk 最多 4 条规则，填一个 `PBESecondaryHashEntry`

对应结构：
- [pbe_compile.h:51](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:51)

填充内容：

1. `ruleIndex[slot]`
- 指向 `ruleMeta` 的下标

2. `keyValue[slot]` / `keyMask[slot]`
- 运行期做 key 过滤用

3. `ruleVector`
- [pbe_compile.cpp:616](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:616)

把规则尾部最多 8 字节右对齐写进去，并做大写归一化：
```cpp

```

4. `tableControl`
- [pbe_compile.cpp:620](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:620)

5. `tailMask`
- [pbe_compile.cpp:621](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:621)

所以：
- `tailOnlyMask = tailMask & ~headMask`
就是“每个 slot 的最后一个有效字节”。

## 8. `pbePrimaryBitmapHasValue()` 判断位图是否有值，是否可以向量化？

对应代码：
- [pbePrimaryBitmapHasValue(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:410)
- [pbeBatchBitmapMask(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:615)

**短答**
可以做一些批量化，但“真正向量化”的收益和实现难度没有那么理想。

**为什么**
当前判断本质是：

```cpp
bitmap[idx / 8] & (1 << (idx % 8))
```

问题在于 `idx` 是当前 key，对 4 个 lane 来说：
- `idx/8` 对应的字节地址通常是离散的
- 不是连续内存

1. 要么做 gather-like 读字节
2. 要么先软件 gather 成连续小数组
3. 再做向量逻辑

这比连续数组做 SIMD 要别扭得多。

**当前收益判断**
这块当然可以优化，例如：
1. 在 `Batch4` 里展开成 4 路无分支位测试
2. 如果 4 个 `idx/8` 落在同一个 bitmap byte，可以合并判断
3. 进一步可以做“software gather + packed test”

但它通常**不是当前最大热点**。

以你现在的性能表现看，真正更重的部分还是：
- `pbeProcessEncodedRange(...)`
- `pbeRuleExactMatch(...)`

所以这块可以优化，但我不会把它排成第一优先级。

## 9. L2 预筛这部分不懂，需要更详细说明每个函数和算法原理

对应代码：
- [PBEPositionContext](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:88)
- [pbeComputeValidMask8(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:165)
- [pbeBuildLaneWindow32FromWindow(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:184)
- [pbeEntryLaneMaskFromByteMatches(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:417)
- [pbeEntryMatchMaskFromContextScalar(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:445)
- [pbeEntrySingleSlotMatchMaskFromContext(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:468)
- [pbeEntryMatchMaskFromContextVector(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:502)

我按数据流讲。

### 第 1 步：构造当前输入位置的 suffix 上下文
在 `PBEPositionContext` 里缓存：
- `window64`
- `laneWindow32`
- `validMask32`

`window64`：
- 当前 `endPos` 往前最多 8 字节
- 用一个 `u64` 表示

`laneWindow32`：
- 把 `window64` 变成 8 字节 suffix 视图
- 再复制 4 份
- 形成 `32B`

对应函数：
- [pbeBuildLaneWindow32FromWindow(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:184)

也就是把：
```text
[win8]
```
复制成：
```text
[win8][win8][win8][win8]
```

这样就能和一个 L2 entry 的：
- `ruleVector[32]`
直接按字节对齐比较。

### 第 2 步：计算哪些字节在当前位置是“真实存在”的
对应函数：
- [pbeComputeValidMask8(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:165)

因为 streaming/history 场景下，当前 endPos 前面不一定真的有完整 8 字节。  
所以这个函数会算一个 8-bit mask：
- 哪些 suffix 字节是有效的
- 哪些是越界补 0 的

然后复制成：
- `validMask32`

这样预筛时不会把“根本不存在的历史字节”当真去比较。

### 第 3 步：把 entry 里 4 个 slot 的 suffix 一次性拿来比
L2 entry 结构：
- `ruleVector[32]`：4 条规则 x 每条 8 字节 suffix
- `headMask`
- `tailMask`
- `ruleCount`

当前算法并不是直接对整条规则做 confirm，而是先问：

**“这个 entry 里的哪几个 slot，看起来可能命中？”**

返回值就是：
- `laneMask`
- bit0..bit3 对应 slot0..slot3

### 第 4 步：单槽 entry 走轻量快路径
对应函数：
- [pbeEntrySingleSlotMatchMaskFromContext(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:468)

如果 `ruleCount == 1`：
- [pbeEntryMatchMaskFromContextVector(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:509)
直接走单槽快路径

算法是：
1. 先取 `tailOnlyMask = tailMask & ~headMask`
   - 也就是最后一个关键字节
2. 最后一个字节不等，直接失败
3. 再补查 `headMask` 对应的前导字节
4. 都相等才返回命中

为什么这么做：
- 单槽 entry 不值得跑完整 32B 预筛
- 先最后一个字节，再前面字节，成本更低

### 第 5 步：多槽 entry 走 laneMask 预筛
对应函数：
- [pbeEntryMatchMaskFromContextVector(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:502)

如果 `ruleCount > 1`：
1. 把 `ctx->laneWindow32` 分成两个 16B
2. 把 `entry->ruleVector` 分成两个 16B
3. 做字节相等比较
4. 得到一个 32-bit 的 `byteMatchMask`
   - 哪个字节相等，对应 bit 就是 1

然后：
- [pbeEntryLaneMaskFromByteMatches(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:417)
把这个 32-bit byte match mask 归约成 4-bit lane mask

### 第 6 步：lane mask 的归约规则是什么
对应函数：
- [pbeEntryLaneMaskFromByteMatches(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:417)

它对每个 slot 做：

1. 看这个 slot 有没有 `tailMask`
2. 最后一个字节 `tailOnlyMask` 是否全部满足
3. 头部字节 `headMask` 是否全部满足
4. 都满足才把这个 slot 加进 `laneMask`

也就是说，最终 lane 命中的判定不是“只要有一个字节相等”，而是：
- 这个 slot 的所有关键 suffix 字节都满足

### 第 7 步：通过预筛的 slot 才继续进 key / groups / confirm
对应函数：
- [pbeProcessEncodedRange(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:531)

流程是：

1. 先 decode `encoded -> offset + count`
2. 遍历这个 key 对应的连续 L2 entries
3. `laneMask = pbeEntryMatchMaskFromContextVector(...)`
4. `laneMask == 0` 就整项跳过
5. 否则只遍历命中的 slot
6. 对这些 slot 再做：
   - `((ctx->key ^ kv) & km) == 0`
   - groups
   - `pbeRuleExactMatch(...)`

### 一个重要补充
当前 L2 结构里还有：
- `tableControl[32]`

但**当前运行期预筛实际上没有直接使用它**。  
当前真正参与预筛的是：
- `ruleVector`
- `headMask`
- `tailMask`
- `validMask32`

所以 `tableControl` 现在更像：
- 结构里已经准备好了
- dump/inspect 有用
- 未来可以继续深化预筛

但它不是当前 L2 热路径的核心判断依据。

## 11. `PBECompileArtifacts` 里的 `windowBytes` 为什么是 8？可以调整吗？

对应代码：

**为什么是 8**
因为当前整个 PBE 设计就是围绕“**尾部 8 字节窗口**”建立的。

这 8 的来源不是随便取的，而是整个结构都绑死在它上面：

1. selector 候选空间是 8 字节 = 64 bit
- [pbe_compile.cpp:29](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:29)

2. `window64` 是 `u64`
- [pbe_engine.c:141](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:141)

3. 每个 L2 slot 只存 8 字节 suffix
- [pbe_compile.h:21](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.h:21)

4. `ruleVector/tableControl`
- 4 条规则 x 8 字节 = 32B

5. `headMask/tailMask`
- 也是按 32 个 byte lane 来编码的

6. `bextMask`
- 用 `u64a`，也正好覆盖 64 bit

**当前它能不能调**
严格说：
- **字段上可以存别的值**
- 但**当前实现并没有真正把它做成可配置参数**

因为运行期主路径里实际上还是写死按 8 来跑的，例如：
- [pbeBuildPositionContext(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:286)

这里调用的是：

```cpp
pbeLoadWindow64Normalized(..., PBE_RUNTIME_BYTES_PER_RULE_SLOT)
```

不是 `hdr->windowBytes`

所以当前 `windowBytes` 更多是：
1. 序列化字段
2. 布局描述
3. 未来扩展预留

**而不是当前真的可调的 runtime knob**

**结论**
现在不能把它当成一个“改个值就能生效”的参数。  
如果你真要改成 4、16 或别的大小，需要连带改：

1. selector 选择空间
2. `window64` 类型
3. `bextMask`
4. L2 slot 大小
5. `ruleVector/tableControl`
6. `headMask/tailMask`
7. prefilter / confirm / tests

所以这本质上是一个结构 redesign，不是参数微调。

## 12. 运行期 `exactEncoded` 和 `wildcardEncoded` 分别表示什么？

对应代码：
- [PBEPositionContext](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:88)
- [pbeBuildPositionContext(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:281)
- [pbeRunNaive(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:708)
- [pbeRunBatch4(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:766)
- [pbeDecodePrimaryValue(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:828)

**先说定义**
它们都是一级哈希表里的 `u32` 编码值。

编码格式：
```text
low 18 bits  = secondaryOffset
high bits    = entryCount
```

用：
- [pbeDecodePrimaryValue(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:828)
来解码。

### `exactEncoded`
表示：

**当前 `endPos` 提取出的 key，对应的一级哈希 exact bucket 的编码值**

也就是：
1. 先用当前输入位置算出 `ctx->key`
2. `ctx->primaryIdx = key`
3. 如果 bitmap 表示这个 key 非空
4. `exactEncoded = primaryHashTable[key]`
5. 否则为 0

### `wildcardEncoded`
表示：

**一级哈希表里 key=0 这个 wildcard bucket 的编码值**

这个 bucket 存的不是“key 真的是 0 的 exact 规则”，而是：

**所有 `keyMask != fullMask` 的规则**

对应编译期逻辑：
- [pbe_compile.cpp:562](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_compile.cpp:562)

```cpp
bucketKey = (keyMask == fullMask) ? keyValue : 0U;
```

也就是说：
- exact 规则 -> 各自 exact key
- partial / don't-care 规则 -> 全部进 `key=0`

### 运行期怎么用
当前运行期顺序是：

1. 先处理 `exactEncoded`
2. 再处理 `wildcardEncoded`
3. 如果二者相同，就避免重复处理

对应：
- [pbeRunNaive(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:749)
- [pbeRunBatch4(...)](d:/work/2026/Hyperscan/code/hyperscan/src/fdr/pbe_engine.c:803)

**举你 inspect 里的例子**
你那个 6 条规则例子里：
- `alpha`
- `delta`
- `gamma`
是 exact bucket
- `ALPHA`
- `beta`
- `THETA`
在 wildcard bucket

所以对某个具体位置：
- `exactEncoded` 可能指向 `L2[2]`、`L2[3]`、`L2[4]` 某一个
- `wildcardEncoded` 则固定指向 `L2[1]`

所以这两个字段的语义就是：

1. `exactEncoded`
   - “当前 key 的精确二级入口范围”

2. `wildcardEncoded`
   - “全局 key=0 的模糊二级入口范围”
